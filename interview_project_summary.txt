项目问题总结（面试版）

1. 推荐链路一开始不稳定，用户输入“我要租房”“给我推荐房子”后，有时不能进入真正的查库推荐流程。
问题原因：
- 后端多个节点里的中文提示词和系统文案出现乱码。
- 意图识别和信息抽取依赖这些提示词，乱码后模型路由不稳定。
解决方式：
- 修复主图和推荐子图中的中文提示词。
- 明确区分 recommend_house、reserve_house、get_info、others 的路由规则。


2. 用户回复“需要”后，预约流程没有继续。
问题原因：
- 主图里“需要 -> 预约子图”的判断逻辑曾受乱码影响。
- 前端对 LangGraph interrupt 返回结构解析不完整，导致中断恢复失败。
解决方式：
- 修复主图中 should_reserve 的判断逻辑。
- 修复前端 interrupt 解析和恢复流程，确保能继续追问房源名、手机号、身份证号。


3. 前端消息结构混乱，思考过程、正式回答、预约提示会覆盖或串位。
问题原因：
- 前端不是按“回合”组织消息，而是按事件流临时往页面插 DOM。
- 旧实现复用了全局消息节点，导致不同轮次之间互相污染。
解决方式：
- 改成每次用户发送消息都创建一个新的回合容器。
- 回合内分离“思考过程”和“最终回答”。
- interrupt 提示、预约结果、查询结果都作为当前回合中的独立回答显示。


4. 推荐内容在页面里被重复输出很多次。
问题原因：
- 前端把流式返回的 messages/partial 每一个增量片段都当成了一条新的回答。
- 结果整段推荐内容被重复渲染。
解决方式：
- 给每轮回答绑定唯一的流式输出块。
- partial 事件只更新当前流式块，不再重复创建新消息节点。


5. 预约完成后，后续查询历史信息时又被错误地下单。
问题原因：
- reserve_graph 中 title、phone、id_card 等预约字段在流程结束后没有清空。
- 后续新问题如果误进预约流程，会复用旧状态再次生成订单。
解决方式：
- 在 finalize_reserve_result 后清空预约相关状态字段。
- 同时收紧主图意图识别，避免普通查询问题误进预约流程。


6. 用户可以输入一个根本没推荐过的房源标题，例如“别墅”，系统仍然能生成预约工单。
问题原因：
- 预约流程只校验字段是否填写，没有校验预约标题是否合法。
- 缺少业务约束，导致脏数据进入预约记录。
解决方式：
- 增加标题校验：预约标题必须来自当前会话推荐结果。
- 如果标题不在推荐上下文中，则要求用户重新输入。


7. 云服务器部署时，前端能访问失败，后端 /docs 正常。
问题原因：
- 后端 API 服务和前端静态页面服务是两个独立服务。
- 后端 8001 通了，但前端静态服务 5500 当时没有启动。
解决方式：
- 明确前端和后端的职责：
  - 前端静态服务：5500
  - 后端 API 服务：8001
- 单独启动前端静态服务，并检查监听端口和访问路径。


8. 部署排查时，一度以为是 SQL 慢，但实际不是数据库本身的问题。
问题原因：
- 页面卡在 sql_db_schema 附近时，表面像数据库慢。
- 但真正问题往往可能出在后端运行环境、服务状态、流式链路或日志不可见。
解决方式：
- 把前后端都改成后台运行并落日志。
- 用日志定位是卡在 sql_db_schema、generate_query，还是卡在前端渲染层。
- 不先拍脑袋认定是 MySQL 问题，而是先确认运行链路每一步的状态。


9. 云服务器上重新启动后端时，启动失败。
问题原因：
- 服务器当前 shell 使用的是错误的 Python 环境。
- 日志显示 langgraph-api 未安装，且 Python 版本不满足要求。
解决方式：
- 先确认原本能运行的环境和启动方式。
- 不盲目重启，优先检查：
  - 当前 Python 版本
  - 当前 langgraph 命令来自哪个环境
  - 是否存在虚拟环境
- 把服务改成可落日志的启动方式，便于后续定位。


10. 这个项目最重要的工程经验
- Agent 项目最难的往往不是“模型会不会答”，而是：
  - 状态流转是否正确
  - interrupt 是否能恢复
  - 前端如何消费流式事件
  - 多轮会话里的中间状态是否清理干净
- 真正影响可用性的 bug，很多不是模型本身问题，而是工作流、状态管理、前后端联调和部署链路的问题。
